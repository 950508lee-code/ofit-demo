# 업무지식 체계 설계 (2026-10-26, 1단계 구현됨)

> **업무의 기준은 조직이 관리하고, 현장의 경험은 업무에 축적된다.**

화면보다 먼저, 지식이 **생기고 → 쌓이고 → 퍼지고 → 올라가고 → 돌아오는** 흐름을 정한다. 이 문서는 설계안이며 아직 코드에 넣지 않았다. ‘정할 것’은 사용자 판정을 받은 뒤 이 문서와 `STRUCTURE.md`에 적는다.

## 1. 지금 있는 것 (코드 기준 사실)

| 지금 이름 | 단위 | 누가 고치나 | 누가 읽나 |
|---|---|---|---|
| 업무 표준(반복업무 이름·주기) | 업무마다, 조직에 하나 | 누구나 올리고 분류 관리자(없으면 총괄)가 승인 | 조직 누구나 |
| 처리 순서·주의 | 반복업무마다, 조직에 하나 | **그 업무를 맡은 사람 누구나 승인 없이 바로** | 조직 누구나 |
| 업무 안내 | 부서 × 업무 | 그 부서에서 그 업무를 맡은 사람 | 같은 부서만 |
| 지난 기록(완료 한 줄) | 회차마다 | 끝낸 사람이 저절로 | 같은 부서만 |
| 참고자료 | 조직, 업무에 붙임 | 맡은 사람 | 조직 누구나 |

**어긋나는 곳 하나:** 처리 순서는 화면에 ‘조직 공통(업무 표준)’이라고 적혀 있지만, 실제로는 어느 지사 담당자든 승인 없이 고치면 그 반복업무의 순서가 조직 전체에서 바로 바뀐다(`store.ts` `editSteps`). 공통 지식을 ‘조직이 관리’하려면 이 길부터 정해야 한다.

## 2. 세 층

| 층 | 담는 것 (예: 예산·회계) | 누가 쓰나 | 누가 확정 | 누가 읽나 |
|---|---|---|---|---|
| **공통 업무지식** (기준) | 업무 목적, 기본 절차(처리 순서), 공통 기준·근거, 공통 주의 | 누구나 올림 | 분류 관리자(없으면 총괄) | 조직 누구나 |
| **부서 노하우** (현장) | 부서 운영 방식, 자주 생기는 예외, 실제 사례, 협의할 곳 | 그 부서 담당자가 바로 씀 | 확정 없음(현장 글) | 조직 전체(출처 표시, '다른 부서 사례 보기'로) |
| **수행 기록** (원자료) | 완료할 때 남긴 한 줄 | 저절로 | 없음 | 같은 부서만 |

- 공통 업무지식은 새 칸을 만들지 않고 **지금의 처리 순서 + 업무 표준을 키운 것**이다. 목적·공통 기준·공통 주의 몇 줄이 더해진다.
- 부서 노하우는 **지금의 업무 안내 그대로**다. 이름만 쓰임새에 맞게 정리한다(화면 이름은 그대로 둘 수도 있음).
- 공통과 부서는 따로 쓴 두 문서가 아니다. **한 업무지식 화면 안에서 위(공통)·아래(우리 부서)로 이어 읽는다.**

## 3. 흐름

```
 일하면서           담당자가 고름          다른 부서가 읽음        분류 관리자 확정         모두에게
 생김 ─────────▶ 쌓임 ─────────▶ 퍼짐 ─────────▶ 올라감 ─────────▶ 돌아옴
 완료 한 줄         지난 기록 한 줄을       같은 업무의 다른         한 문단을 공통으로        맡은 사람 모두 알림,
 주의 한 줄         부서 노하우로 옮김      부서 노하우를 나란히       (출처 남김)              부서 글엔 '공통에 반영됨'
 업무 안내 고침
```

1. **생김 — 일하면서.** 완료할 때 한 줄, 처리 순서 단계 아래 주의, 업무 안내 고치기. 지금과 같고 **쓰라고 시키지 않는다.**
2. **쌓임 — 기록에서 노하우로.** 담당자가 지난 기록 한 줄(예: “12월은 이월 보고 때문에 20일에 마감”)을 골라 우리 부서 노하우의 예외·사례 칸으로 옮긴다. 기록은 흩어진 원자료, 노하우는 다음 사람이 읽을 글.
3. **퍼짐 — 같은 업무를 맡은 다른 부서가 읽음.** 업무지식에서 ‘다른 부서에서는’ 묶음으로 부서 이름·고친 날과 함께 읽는다(고치기는 그 부서만). 그 업무를 맡은 다른 부서 담당자는 문단마다 **‘우리도 이렇게 함’**을 누를 수 있다(3-3).
4. **올라감 — 부서 노하우 한 문단을 공통으로.** 누구나 문단 하나를 골라 ‘공통으로 올리기’ → 지금의 업무 표준 검토 칸으로 간다(처리할 것). 분류 관리자는 문장을 다듬어 공통의 어느 자리(기본 절차·공통 기준·공통 주의)에 넣고 승인한다. **출처(부서·쓴 사람·날짜)**가 공통 문장 옆에 남는다. ‘우리도 이렇게 함’은 제안이 아니다. 여러 부서가 쓰는 방식은 관리자 화면의 참고 목록에만 보이고, 공식 검토 목록에 섞이지 않는다(3-3). 자동 점수·AI 판정은 쓰지 않는다. 사람이 고르고 사람이 확정한다.
5. **돌아옴 — 공통이 바뀌면.** 그 업무를 맡은 모든 사람에게 ‘확인할 것’ 알림 한 줄(무엇이 바뀌었는지). 출처가 된 부서 문단은 지우지 않고, 기본 화면에서 ‘공통 기준에 반영됨’ 한 줄로 접힌다(3-4).

### 예 (예산·회계)

1. 광진지사 김건강이 업무 안내에 “12월은 이월 보고 때문에 마감을 20일로 당깁니다”를 쓴다.
2. 노원지사 박공단이 업무지식에서 읽고 ‘우리도 이렇게 함’을 누른다. 두 부서가 같은 방식이 된다.
3. 한경영(경영지원 분류 관리자)의 ‘여러 부서가 쓰는 방식’ 참고 목록에 보인다. 김건강이 ‘공통 기준으로 제안’을 따로 누르면 그때 공식 검토 목록에 들어간다. 한경영이 “12월 지출결의 마감은 20일”로 다듬어 공통 주의에 넣는다. 옆에는 출처 ‘광진지사 · 2026.10’이 남는다.
4. 예산·회계를 맡은 모든 사람에게 알림이 간다. 광진지사 문단에는 ‘공통에 반영됨’이 붙는다.

## 3-1. 공개 범위와 고칠 권한 (2026-10-26 사용자 판정, 정할 것 1)

열람과 수정은 따로 정한다.

| 구분 | 읽기 | 고치기 |
|---|---|---|
| 공통 업무지식 | 조직 전체 | 승인된 관리자(분류 관리자·총괄 관리자) |
| 우리 부서 노하우 | 조직 전체 | 우리 부서에서 그 업무를 맡은 사람 |
| 다른 부서 노하우 | 조직 전체 | 그 부서에서 그 업무를 맡은 사람만 |
| 수행 기록 | 그 부서 안 | 지금과 같음 |

- **출처는 늘 보인다.** 다른 부서 노하우에는 부서 이름·고친 날이 붙고, 공통 기준과 글 모양으로 구분한다. 공통 기준은 '조직에서 승인한 처리 기준', 현장 노하우는 '그 부서에서 실제로 쓰는 방법, 다른 부서에 그대로 맞지 않을 수 있음'으로 읽혀야 한다. (예: 광진지사의 '12월 20일 마감'을 노원지사가 조직 기준으로 오해하지 않게.)
- **열 수 있다는 것과 늘 펼쳐 둔다는 것은 다르다.** 업무지식 기본 화면은 공통 업무지식 + 우리 부서 노하우만 보인다. 다른 부서 것은 '다른 부서 사례 보기'를 눌렀을 때만 나온다(부서 이름 목록 → 고르면 그 부서 노하우).
- **조직 전체에 열기 전에 자료마다 공개 범위를 고를 수 있어야 한다.** 개인정보나 내부 사정이 섞일 수 있어서다. 부서 노하우마다 '조직 전체 / 우리 부서만'을 둔다(처음 값은 정할 것 1-1).

## 3-2. 처리 순서: 현장 개선과 조직 표준화는 따로 (2026-10-26 사용자 판정, 정할 것 2)

| 행동 | 결과 |
|---|---|
| 담당자가 처리 순서를 고침 | **우리 부서 방식**으로 바로 반영. 공통 기준은 그대로 |
| '공통 기준으로 제안' (따로 누름) | 분류 관리자(없으면 총괄) 검토 칸으로 |
| 관리자 승인 | 공통 처리 순서에 반영, 출처(부서·날짜) 남김, 맡은 사람 모두 알림 |
| 관리자 반려 | 공통 기준도, 부서 방식도 그대로(부서 노하우는 지우지 않음) |
| 관리자가 직접 고침 | 바로 공통에 반영. **변경 이력(누가·언제·무엇을, 전·후)** 남김 |

- **덮어쓰지 않는다.** 공통 처리 순서가 기본으로 보이고, 부서가 다르게 하는 단계에만 그 아래에 부서 방식 한 줄이 붙는다. 공통이 바뀌어도 부서 글을 고칠 필요가 없다.

  > **③ 담당자에게 보완 요청** — 공통 처리 순서
  > 노원지사 운영 방식 · 메일로 요청하고 3일 안에 회신 확인

- 부서 방식은 단계마다 단다(더하기·바꾸기·빼기 표시). 공통 단계가 나중에 바뀌거나 없어지면, 그 단계에 달린 부서 방식은 '공통이 바뀌었습니다, 확인 필요'로 표시만 하고 지우지 않는다.
- **이미 있는 처리 순서는 공통으로 인정**하되, 이력의 출발점을 **'기존 등록 자료'**로 남겨 승인된 기준과 구분한다. 관리자가 한 번 확인하면 '승인'으로 바뀐다.
- 관리자 직접 변경 이력은 업무지식에서 '바뀐 기록'으로 누구나 볼 수 있다.

## 3-3. ‘우리도 이렇게 함’ — 확인과 표준화 제안은 따로 (2026-10-26 사용자 판정, 정할 것 3)

인기투표가 아니라 **현장에서 실제로 쓰는 방식인지 확인하는 수단**이다. 목표는 가장 인기 있는 방식을 찾는 것이 아니라, 조직 곳곳에 흩어진 검증된 실무 경험을 발견하는 것.

| 행동 | 누가 | 결과 |
|---|---|---|
| ① 우리도 이렇게 함 | 그 업무를 맡은 다른 부서 담당자 | 부서 단위로 붙음(사람 수 아님). 숫자 없이 부서 이름으로 보임: “광진지사 운영 방식 · 노원지사도 이렇게 함”. 관리자에게 알림 없음. 내용은 복사되지 않음 |
| ② 공통 기준으로 제안 | 담당자가 필요하다고 판단할 때 따로 | 관리자의 공식 검토 목록에 들어감(처리할 것) |
| ③ 여러 부서가 쓰는 방식 | (저절로) | 관리자 화면에 따로 있는 **참고 목록**. 검토 요청과 섞지 않고, 부서 수로 자동 승인하거나 순서를 올리지 않음 |

- 숫자·순위·정렬 없음.
- ‘우리도 이렇게 함’은 그 부서 담당자가 언제든 뺄 수 있다.
- 표시는 부서에 붙어 발령으로 사람이 떠나도 남는다. 다만 **그 부서에 지금 그 업무를 맡은 사람이 없으면 ‘지금 쓰는지 확인 안 됨’**으로 구분해 보인다(과거에 썼다는 것이 지금도 쓴다는 보장은 아니므로). 새 담당자가 다시 누르면 확인됨으로 돌아온다.

## 3-4. 공통 기준으로 올리는 단위와 검토 (2026-10-26 사용자 판정, 정할 것 4)

**현장의 노하우를 필요한 만큼만 조직의 공통 지식으로 바꾼다.** 업무 안내 전체를 승인받는 방식은 기존 매뉴얼 관리와 다르지 않다.

- **한 제안 = 한 가지 내용.** 문단 하나, 목록 한 줄, 처리 순서 한 단계의 부서 방식 중 하나.
- **제안자는 내용을, 관리자는 체계를.** 제안 이유와 넣을 자리는 모두 **선택 입력**. 제안자가 공통 기준의 구조를 알 필요는 없다. 최종 위치와 문장은 관리자가 정한다.
- **관리자가 승인 전에 확인할 것:** 문장만이 아니라 **적용 범위**(그 지사만의 내부 일정인지, 조직 전체에 맞는지)와 **기존 기준과의 충돌**. 여러 부서가 같은 방식으로 일한다고 해서 공통 기준으로 맞는 것은 아니다.
- **관리자의 선택:** 그대로 승인(바로 공통 반영) / 다듬어 승인(원문과 다듬은 문장 둘 다 이력에 남김) / 반려(사유가 제안자에게 감).
- **원문은 보존하고, 중복 노출은 줄인다.**

  승인 전
  > 광진지사 노하우: 12월은 마감을 20일로 당깁니다.

  승인 후
  > 공통 기준: 12월은 마감을 20일로 당깁니다.
  > 광진지사 노하우: 공통 기준에 반영됨 (펼치면 원문)

  관리자가 다듬으면서 뜻이 달라졌을 수 있으면 자동으로 중복 처리하지 않는다. 원문과 승인된 기준을 나란히 비교할 수 있게 한다.

## 4. 인수인계·발령 때

새로 맡은 사람은 업무지식에서 **공통(기준) → 우리 부서 노하우 → 다른 부서에서는(참고)** 순으로 읽는다. 지난 기록은 내 업무에서 본다(지금과 같음).

## 5. 지금 데이터에 얹는 방법 (구현은 나중, 메모)

- 공통 업무지식: `commonGuides[unitId] = {html, by, at, sources[]}`. 처리 순서·업무 표준은 지금 자리 그대로 공통 층으로 읽는다.
- 처리 순서 단계에 오래가는 id를 붙인다(지금은 순번). 부서 방식: `deptSteps['부서:반복업무'][단계id] = {kind: 'add'|'change'|'skip', text, by, at}`.
- 공통 변경 이력: `history[]` = `{target, before, after, by, at, how: 'seed'|'approved'|'admin', source?}`. 지금 처리 순서는 `how: 'seed'`(기존 등록 자료)로 한 줄씩 넣는다.
- 지금 `editSteps`(맡은 사람이 공통을 바로 고침)는 부서 방식 쓰기로 바꾸고, 공통 고치기는 관리자만.
- 올리기: `Proposal`에 종류를 더한다(`duty` 지금 것 / `steps` 처리 순서 고침 / `knowledge` 노하우 문단). 검토 화면과 알림(처리할 것)은 지금 것을 그대로 쓴다.
- 문단 식별: 부서 노하우 문단마다 id를 붙여야 ‘우리도 이렇게 함’·‘공통에 반영됨’을 문단에 달 수 있다(`Guide.tsx` 정리기에서 부여).
- ‘우리도 이렇게 함’: `alsoUse['부서:업무:문단id'] = [{deptId, by, at}]`. ‘지금 확인 안 됨’은 저장하지 않고 그 부서에 지금 맡은 사람이 있는지로 그때그때 가른다.
- 저장 모양이 바뀌므로 `KEY`를 올린다.

### 8-2. 점검에서 걸린 것 (줄이자는 제안)

1. **‘기존 등록 자료’를 관리자가 하나씩 확인해 승인으로 바꾸는 것** — 시연 기준표만 해도 반복업무 26개의 순서를 확인하는 밀린 일이 생긴다. → 확인 목록을 만들지 않는다. ‘기존 등록 자료’는 이력에만 보이고, 관리자가 그 순서를 처음 고치거나 제안을 승인할 때 자연스럽게 승인 기록이 쌓인다.
2. **중복 접기를 누가 판단하나** — 관리자에게 ‘뜻이 같은가’를 고르게 하면 검토가 한 단계 는다. → 문장 그대로 승인되면 저절로 접는다. 다듬어 승인되면 ‘다듬어 반영됨 · 비교’로 펼친 채 두고, 그 부서 담당자가 원하면 한 번 눌러 접는다.
3. **공개 범위를 어디에 거나** — 문단마다 고르게 하면 쓸 때마다 판단이 생긴다. → 업무 안내 문서 하나에 하나(조직 전체 / 우리 부서만). 처음 값은 정할 것 1-1.
4. **부서 지식이 두 곳(업무 안내 · 단계별 부서 방식)** — 개념이 하나 는다. 판정대로 두되, 화면에서는 둘 다 ‘○○지사 운영 방식’이라는 같은 말과 같은 모양으로 보여 하나로 읽히게 한다.
