# 업무지식 문서 구조와 '할 일을 누르는 순간' 연결 (2026-10-26, 구현 전 설계)

> **갱신(2026-10-26 사용자):** 아래 다섯 칸은 **확정하지 않는다.** '처리 순서'는 '반복업무'(주기·일정·처리방법·참고자료를 함께 든 관리 대상) 안으로 들어가는 방향. 업무지식이 중심, 오늘·달력은 실행 화면. 연결 흐름 설계는 `docs/FLOW.md`.

> 사용자 판정(2026-10-26): 시안 A(관리 화면)·B(정리된 보고서)·C(위키 문서식) 가운데 **C안을 기본 방향**으로. 단 그대로 채택하지 않고 문서 구조를 먼저 정리한다. **지금은 구현하지 않고, 화면을 더 꾸미지 않는다.**
> OFIT의 핵심(사용자 말): **업무를 맡으면 해야 할 일이 보이고, 할 일을 누르면 처리방법이 보이며, 그 지식은 다음 담당자에게 그대로 이어진다.**
> C안은 '지식이 읽히는 방식'을 고쳤다. 남은 것은 '업무를 수행하는 순간 지식이 어떻게 나타나는가'.

| 요소 | 판정 |
|---|---|
| 목차와 본문 연결 | 채택 |
| 제목 번호 체계(1. 2. 2.1) | 채택 |
| 제목별 고치기(그 부분만) | 채택 |
| 연속된 문서형 본문(관리 카드 여러 장 대신) | 채택 |
| 오른쪽 요약 표 | 수정: 색 머리띠 없음, **분류 · 담당자 · 반복업무 수**만(반복업무 이름 나열은 본문과 겹쳐 뺌) |
| 목차 | 조건부: 720px 기준은 버림. **이동할 만한 내용이 충분할 때만**. 빈 문서에는 목차 대신 작성 시작점 |

| 최상위 구조 | 다섯 개로 고정(아래 2장). 담당자가 쓰는 소제목은 업무 안내 **안으로** |

## 2. 문서 뼈대 — 최상위는 고정, 자유로운 글은 한 칸 안에

```
인사·복무                                   [요약 표: 분류 · 담당자 · 반복업무 4개]
(목차 — 내용이 충분할 때만)

1. 업무 개요      이 업무가 무엇인지(한두 문장)
2. 업무 안내      담당자가 자유롭게 쓰는 지식·노하우   ← 부서마다, 맡은 사람이 고침
   2.1 한 달 흐름          (작성자가 붙인 소제목)
   2.2 자주 생기는 일      (작성자가 붙인 소제목)
3. 처리 순서      반복업무별 처리방법                   ← 조직 공통(관리자가 고침) + 단계 아래 '○○지사 방식'(담당자)
   3.1 초과근무 승인 · 매주 금요일     조직 공통
   3.2 월간 복무 점검 · 매월 말일      조직 공통
   3.3 근태 확인 · 매일                아직 없음
4. 참고자료      파일 이름과 있는 곳, 링크            ← 맡은 사람이 붙이고 뗌
5. 변경 기록      누가 무엇을 바꿨는지
```

- 작성자가 업무 안내에 소제목을 더하거나 빼도 1·3·4·5의 번호와 자리는 흔들리지 않는다.
- 처리 순서의 '조직 공통' 표시는 3.n 제목 옆 작은 글자 하나. 고치기 단추: 공통 순서는 분류·총괄 관리자에게만, '우리 부서 방식'은 그 업무 담당자에게만 보인다.

## 3. 남은 구조 쟁점 (하나씩 판정)

### 3-1. 업무 개요는 어디서 오는가
- **안 가(추천):** 업무 안내의 **맨 앞 문단**을 개요로 보인다. 이미 정한 '업무 개요 = 맨 앞 문단 조금 크게'(업무 안내 문서형 판정)와 같고, 새 입력칸·새 자료가 없다. 개요가 비면 1번 칸에 "이 업무가 무엇인지 한두 문장으로 적어 두세요 · [쓰기]".
- 안 나: 개요를 따로 쓰는 칸. 업무 안내와 따로 고칠 수 있지만 쓸 곳이 하나 는다.

### 3-2. 업무 안내와 처리 순서의 경계
- 업무 안내 = **업무 전체**에 걸친 것(흐름, 예외, 사람·부서 사이 사정, 노하우).
- 처리 순서 = **반복업무 하나**를 하는 방법. 특정 반복업무에만 해당하는 요령·실수는 그 반복업무의 '우리 부서 방식'이나 '주의'로.
- 화면은 이 경계를 강제하지 않는다('쓰라고 시키지 않는다'). 다만 업무 안내를 고칠 때 칸 밖에 한 줄 기준을 보인다(처리 순서 쓰기와 같은 방식, `docs/WRITING.md`).

### 3-3. 변경 기록에 무엇이 들어가는가
- 문서가 바뀐 것만: 공통 처리 순서 고침(이미 이력 있음) · 우리 부서 방식 고침 · 업무 안내 고침 · 참고자료 붙임/뗌 · 업무 표준 승인으로 반복업무 더해짐. 오늘 화면 알림 한 줄의 '내 업무에서 바뀐 것'과 같은 원본(`recentChanges`)을 기간 제한 없이.
- 자료 공백: 업무 안내는 지금 **마지막으로 고친 사람·때만** 남는다(이력 없음). 참고자료 뗌도 기록이 없다. 기록을 더 남길지는 따로 판정.
- 수행 기록(지난 기록)·거쳐 간 사람은 '문서가 바뀐 것'이 아니다. 지난 기록은 내 업무가 주인(이미 판정). → 업무지식에서는 요약 표의 담당자 칸 옆 '지난 담당자', 끝에 '지난 기록 n건 · 내 업무에서 보기' 한 줄로 둘지 판정.

### 3-4. 참고자료는 업무에 붙는가, 반복업무에 붙는가
- 지금은 업무(인사·복무)에 붙는다. 할 일 상세에서 '월간 복무 점검'을 열었을 때 업무의 참고자료를 모두 보이면 된다(대개 몇 개). **새 자료 없음.**
- 반복업무마다 붙이기는 목록이 길어질 때만 다시 본다.

## 4. 같은 지식, 두 맥락

| | 업무지식 문서 | 할 일 상세 판 |
|---|---|---|
| 언제 여나 | 업무 전체를 이해할 때(처음 맡음, 인수인계 받음, 찾기) | 오늘 그 일을 할 때(할 일 줄을 누름) |
| 보이는 것 | 1~5 전체 | **그 반복업무에 필요한 것만** |
| 고치기 | 여기서만(제목별 고치기) | 하지 않음. '업무지식에서 고치기'로 그 칸에 바로 감 |

### 할 일 상세 판 — 신규 직원의 다섯 질문 순서로

| 질문 | 보일 것 | 원본 | 지금 |
|---|---|---|---|
| 언제 해야 하지? | 날짜 · 리듬(매월 말일) | 반복업무 규칙 | 있음 |
| 무엇부터 해야 하지? | 처리 순서(체크칸) + 단계 아래 '○○지사 방식' | 문서 3.n | 있음 |
| 실수하기 쉬운 건? | 주의 줄(해당 단계 바로 아래) | 문서 3.n | 있음 |
| 어떤 시스템·자료? | **참고자료(이름 · 있는 곳 · 링크)** | 문서 4 | **없음 — 더할 것** |
| 지난번엔 어떻게? | 지난번 한 줄(날짜 · 사람 · 메모) | 수행 기록 | 있음 |
| 더 알고 싶으면 | '업무지식에서 보기 · 3.2 월간 복무 점검' — 문서의 그 칸으로 바로 | 문서 | 이름표로 문서 맨 위까지만 감 |

- 할 일 상세에서 **빼는 것**(이미 점검 문서 후보): "이름·주기는 … 업무 표준에서 바꿉니다" 안내 상자, 공통 순서 출처·바뀐 기록·우리 부서 방식 단추 줄. 고치기는 문서 쪽 한 곳에서.
- 처리 순서가 비어 있으면: "아직 처리 순서가 없습니다" 한 줄 + '업무지식에서 쓰기'(그 칸으로 바로). 일은 그대로 완료할 수 있다.

### 거꾸로: 문서에서 할 일로
- 3.n 제목 줄에 '다음 10월 30일' 같은 다음 회차를 회색으로 보일지 판정(내 업무의 업무 줄과 같은 정보). 누르면 그날 할 일 상세.

## 5. 인수인계와의 관계
- 업무 안내·처리 순서·참고자료·변경 기록은 모두 **업무(자리)에 붙어 있어** 인수인계·발령 때 따로 옮길 것이 없다. 다음 담당자가 할 일을 누르면 같은 처리 순서·참고자료가 그대로 보인다 — 핵심 문장의 세 번째 마디.

## 6. 하지 않을 것
- 화면 꾸미기(색·글자 크기 조정)는 이 구조가 정해질 때까지 하지 않는다.
- 업무지식 2·3단계(공통 기준 제안·'우리도 이렇게 함')는 계속 동결.
