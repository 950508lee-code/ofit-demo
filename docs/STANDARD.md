# 하나의 업무, 하나의 표준, 여러 담당자 (2026-10-26 사용자 판정, 구현 전)

> **목적을 바로잡음(사용자):** "업무를 인수인계 없이도 쉽게 이어받는 시스템"은 목적과 효과를 뒤집은 말이었다. 정확히는
> **업무를 표준화하여 담당자가 바뀌어도 동일한 체계로 업무가 수행되도록 한다.** 인수인계가 쉬워지는 것은 표준화의 **결과**다.
> **설계 기준: 하나의 업무, 하나의 표준, 여러 담당자.** 업무의 기준과 지식은 조직이 공유하고, 업무의 배정과 수행 이력은 담당 조직별로 관리한다.
> **철회:** 부서별 업무지식 문서를 기본 구조로 두는 것.
> 이 원칙은 '업무관리를 위해 새로운 업무를 만들지 않는다'와도 맞는다.

## 1. 표준화할 세 가지

| 구분 | 표준화 대상 | 기대 효과 |
|---|---|---|
| 업무 체계 | 업무 분류 · 명칭 · 담당 범위 | 누가 맡더라도 같은 업무 구조 |
| 업무 수행 | 반복주기 · 처리 순서 · 확인사항 | 담당자가 달라도 일관된 수행 |
| 업무지식 | 처리방법 · 참고자료 · 업무 노하우 | 개인의 경험이 조직의 자산으로 |

- **표준화 ≠ 획일화.** 공통 구조와 기준을 정하고, 정당한 예외는 **표준 안에서 적용 조건으로** 관리한다(예: "지사장 결재까지 — 해당: ○○지사"). 지사마다 따로 쓴 문서로 두지 않는다.
- **표준화 ≠ 중앙집중식 승인.** 누구나 개선에 참여(제안)하고, 공식 기준이 바뀌는 권한·절차는 따로 설계한다. 제안과 기준 변경은 다른 일이다.

## 2. 원본과 화면

```
업무 표준(원본, 조직에 하나)
 └ 업무 「인사·복무」 ── 분류 · 명칭 · 담당 범위 · 개요 · 노하우
     └ 반복업무 「초과근무 승인」 ── 반복주기 · 처리 순서 · 확인사항(주의) · 예외(적용 조건) · 참고자료
            │
   배정(업무분장)       노원지사 담당자 A          광진지사 담당자 B
            │                 │                         │
   수행                 오늘·달력 회차 · 수행 기록   오늘·달력 회차 · 수행 기록
```

- 업무지식 = 표준을 읽고 고치는 화면(색인 + 반복업무 문서, `docs/FLOW.md`).
- 오늘·달력 = 표준의 반복주기가 배정된 담당자에게 회차로 나타나는 화면.
- 할 일 상세 = 그 회차에 표준 처리방법·참고자료가 붙어 나오는 화면.
- 수행 기록 = 담당자와 소속 조직에 남는다(이미 그렇게 저장함: 기록에 그때의 부서·업무를 박음).
- 담당자가 바뀌어도 표준은 그대로.

## 3. 지금 코드와 다른 점 (고칠 때 다룰 것, 아직 손대지 않음)

| 지금(업무지식 1단계, 2026-10-26 구현) | 새 원칙에서 |
|---|---|
| 업무 안내가 **부서마다** 따로(`guides['부서:업무']`) | 업무마다 하나(조직 공유). 옛 부서별 글을 어떻게 합칠지 판정 필요 |
| 처리 순서 단계 아래 '○○지사 운영 방식'(`deptWays`) | 표준 안의 **예외(적용 조건)** 로 옮기거나, 표준 개선 제안으로 |
| 공개 범위 '우리 부서만 / 조직 전체'(`knowScope`), '다른 부서 사례 보기'(`otherCases`) | 모두 조직 공유라 필요 없어짐 |
| 수행 기록은 같은 부서만 보임 | 그대로(배정·수행은 담당 조직별) |
| 반복업무·주기 = 업무 표준(제안 → 분류·총괄 관리자 승인) | 그대로 |
| 기관 등록 때 업무 기준표 CSV(직렬·단위업무·반복업무·주기) 올리기 | 그대로 — **업무 체계·반복주기는 처음부터 채울 길이 있음** |
| 동결된 2단계 코드(`git stash`): 현장 내용을 공통 기준으로 제안 → 관리자 반영(`proposeKnow`·`approveKnow`) | 새 원칙의 '제안 → 기준 변경'과 거의 같은 일. 되살릴지 판정 |

## 4. 다음 판정: 누가 표준을 처음 만들고, 누가 고치나

문제: OFIT은 처음에 비어 있고 직원이 직접 채워야 한다. 업무 체계·주기는 기준표 CSV로 채울 수 있지만, **처리 순서·확인사항·참고자료·노하우는 비어서 시작한다.** 이걸 누가 채우느냐가 풀리지 않으면 '하나의 표준'이 작동하지 않는다.

| 안 | 처음 만들기 | 고치기 | 좋은 점 | 걸리는 점 |
|---|---|---|---|---|
| 가. 관리자만 | 분류·총괄 관리자 | 관리자 | 일관성 | 관리자 몇 명이 전 업무를 써야 해서 오래 빈다 |
| 나. 누구나 바로(위키) | 담당자 누구나 | 누구나, 이력·되돌리기 | 빨리 찬다 | 178곳이 한 표준을 수시로 바꿔 '표준'이 아니게 된다 |
| **다. 비어 있으면 바로, 있으면 제안(추천)** | 그 업무 담당자 누구나 — **빈 칸에 처음 쓴 것은 바로 보이되 '검토 전'** 표시 | 이미 있는 표준은 **제안 → 분류 관리자 확인**. 관리자가 확인하면 '검토 전'이 '표준'으로 | 첫 담당자가 바로 채워 비어 있는 기간이 짧다. 한번 정해지면 흔들리지 않는다 | 같은 때 여러 지사가 처음 쓰면 먼저 쓴 것이 초안, 나머지는 제안으로 쌓인다 |

- 다안에서 노하우(업무 안내의 팁)는 표준보다 가볍게: 누구나 덧붙이고 쓴 사람·지사가 보이며, 관리자가 표준(처리 순서·확인사항)으로 올릴 수 있다.
- 업무 체계·반복주기는 어느 안이든 지금처럼 제안 → 승인.
