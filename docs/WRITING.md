# 처리 순서 쓰기·읽기 (2026-10-26)

다른 작업(저장소 `950508lee-code/nhisreminder`, 문서 `docs/workbaton/33_writing_reading_research.md`)에서 조사하고 사용자가 판정한 것을 오핏에 옮긴 기록이다. 원 조사는 대부분 검색 요약과 2차 인용이라, 숫자(7단계, 5~9개 등)는 기준으로 쓰지 않는다.

## 사용자 판정

| 제안 | 판정 |
|---|---|
| 작성 기준을 입력칸 **밖**에 늘 보이기 | 승인 |
| 질문 대신 작성 기준 문장 주기 | 승인 |
| 주의 위치·항목 수 안내 | 권장만. 강제하지 않는다. 단계 수 제한 없음 |
| 작성 품질 자동 측정(단계 수·문장 길이 경고, 점수) | 보류. 짧다고 좋은 문서가 아니고, 형식 맞추기로 흐를 위험 |
| AI 문서 분석·재구성, 확인 목록과 일정 체크리스트 자동 연결 | 하지 않는다 |

원칙: **좋은 문서의 형태와 좋은 문서를 쓰는 방법은 다르다. 사용자가 작성 규칙을 공부하게 만들지 않는다.** 편집기가 보장하는 것은 읽기 쉬운 형식과 빠뜨리지 않게 돕는 안내까지이고, 내용이 맞는지는 담당자와 조직 기준의 몫이다.

## 오핏에 넣은 것 (`src/Cards.tsx` StepsEditor, DutyCard)

- **작성 기준(칸 밖, 늘 보임):** "한 단계에 한 가지 작업을 적으세요. 사용하는 시스템과 수행할 행동을 구체적으로 적으면 좋습니다." 입력칸 안 안내(placeholder "무엇을 하나요")는 뺐다. 칸 안 안내는 입력하면 사라지고, 이미 채운 칸으로 오인되기 쉽다는 조사 결과 때문이다.
- **주의 줄:** 단계마다 '주의 넣기'를 누르면 그 단계 바로 아래에 주의 줄이 생긴다(`Step.warn`). 주의가 있으면 기준 한 줄이 더 보인다: "주의: 실수하기 쉬운 상황이나 예외사항을 적으세요." 업무 카드에서는 체크 칸 없이, 앞 단계 아래에 '주의' 상자로 보인다. 경고는 문서 끝에 모으면 잘 안 읽히고 해당 단계 바로 앞뒤에 둘 때 낫다는 지침(영국 HSE 등)을 따른 것이다.
- 확인 목록은 따로 만들지 않는다. 오핏에서는 처리 순서가 곧 회차의 체크리스트이고, 작성 경로가 하나라서 중복이 없다.

## 조사 요약 (확인 수준: 대부분 요약·2차)

- 쓰게 만드는 것: 보상보다 "내가 쓸 만한 걸 안다"는 감각과 남을 돕는 즐거움(공공부문 조직 설문, Kankanhalli 외 2005). 포인트·배지는 근거 약함.
- 안 쓰게 만드는 것: 시간, 무엇을 써야 할지 모름, 평가받는 두려움. 첫 기여가 거절되면 떠난다(위키백과, Halfaker 외 2011).
- 사람은 훑어 읽는다. 제목은 내용을 말하고 첫 줄에 핵심을 둔다.
- 정보는 종류를 나누고 섞지 않는다(Information Mapping, Diátaxis). 처리 순서 안에 긴 설명을 섞지 않는다.
- 처리 순서는 한 단계에 한 동작. 길면 나누기를 권한다(제한은 두지 않는다).
